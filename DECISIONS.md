# Decisions

Major technical decisions for cookingwithtrevor, newest last.

| Date | Decision | Reason | Alternative considered |
| --- | --- | --- | --- |
| 2026-09-24 | Next.js (App Router) + TypeScript | Server-rendered pages give the blog SEO and shareable links; TypeScript reads well in a portfolio. | Astro: faster static blog, weaker for signed-in app features. |
| 2026-09-24 | Supabase for Postgres, auth and image storage | One free service covers DB, email/Google login and photos; row-level security enforces per-user data without a custom backend. | Firebase: non-relational, poor fit for recipes/ingredients/ratings. |
| 2026-09-24 | Supabase Auth (via `@supabase/ssr`) instead of a separate auth library | Fastest path on a weekend timeline and plugs straight into RLS policies. | Auth.js: more flexible but must be bridged to Supabase RLS manually. |
| 2026-09-24 | Tailwind CSS | Quick mobile-first layouts (R8) and a small CSS bundle for the <2s load target (R13). | CSS Modules: no dependency, slower to build responsive UI. |
| 2026-09-24 | Vercel hosting | Free, built by the Next.js team, auto-deploys on push for a live demo URL. | Netlify: also free, Next.js support lags slightly. |
| 2026-09-24 | Folder structure: `app/` routes per MVP feature, `components/`, `lib/supabase/`, `supabase/migrations/` | Routes map 1:1 to MVP features; versioned SQL makes schema changes visible in the repo. | Feature folders (`features/recipes/...`): cleaner at scale, overkill for the MVP. |
| 2026-09-24 | `profiles` table linked to Supabase's `auth.users`, filled by a sign-up trigger, instead of a standalone `users` table | Supabase already stores login data; `profiles` holds only public fields (name, role), and column grants stop users changing their own role. | Standalone `users` table synced by app code: duplicates auth data and can drift. |
| 2026-09-24 | One rating/comment per user per recipe, plus a DB-trigger rate limit (3/hour for accounts under 24h, 10/hour after) | Stops rating stuffing and new-account spam at the database, so it holds even if the UI is bypassed. | Rate limiting in app code: easier to tweak, but a direct API call skips it. |
| 2026-09-24 | Header reads login state in the browser, not on the server | Keeps blog pages static and cacheable for the <2s mobile target (R13). | Server-side session in the layout: simpler, but makes every page dynamic. |
| 2026-09-24 | Keep Supabase's default confirmation email for now; if the code exchange fails (link opened in another browser), tell the user their email is confirmed and to sign in. Add `/auth/confirm` (token-hash links) for when custom SMTP is set up before launch. | Editing email templates requires custom SMTP, which needs a domain we don't have yet; a code is only issued after Supabase verifies the email, so "confirmed, please sign in" is accurate. | Turn off email confirmation: simpler, but lets throwaway emails create accounts. |
| 2026-09-25 | Save a post with a `save_recipe` Postgres function (one transaction, runs as the caller so RLS applies) | A failed save can't leave a recipe with missing ingredients or steps. | Separate inserts from the app: simpler, but partial saves on error. |
| 2026-09-25 | Ingredients and steps entered one per line; ingredients parsed into quantity / unit / name with normalized units | Fast to write, and structured data is what the grocery-list merge (R5) needs. Ranges ("2-3") keep no quantity so they're never merged wrongly. | One form row per ingredient: precise, but slow to type. |
| 2026-09-25 | Photos upload from the browser straight to Supabase Storage (admin-only by storage policy, 5 MB, images only) | Avoids Next's 1 MB Server Action body limit and an extra hop through the server. | Upload through a Server Action with a raised body limit. |
| 2026-09-25 | Public pages use a cookie-free Supabase client, are prerendered (ISR), and are revalidated on save with `revalidatePath` | Static, cacheable HTML for SEO and the <2s mobile target (R13); edits show up immediately. | Render on every request: always fresh, but slower and more DB load. |
| 2026-09-25 | zod for form validation | Typed, declarative checks with per-field errors; a common, well-known choice. | Hand-written checks: no dependency, more code to maintain. |
| 2026-09-25 | Recipe pages emit schema.org Recipe JSON-LD | Lets Google show rich results (rating, time, image) for blog posts. | Skip structured data: less work, weaker search listings. |
| 2026-09-26 | A user's library is exactly their `saved_recipes` rows; recipes entered by hand are saved to the library in the same transaction (`save_recipe(..., p_add_to_library)`) | One source of truth for "my library", and admin blog drafts (also private) stay out of the admin's library. | Library = saved rows + all own private recipes: mixes drafts into the admin's library. |
| 2026-09-26 | The Save button on post pages reads and writes `saved_recipes` from the browser | Post pages stay static and cacheable; RLS limits users to their own rows. | Server-side saved state: makes every post page dynamic per user. |
| 2026-09-26 | Library search and tag filters run in the server component over the user's full library | A personal library is small, so this is simple and fast, with no query escaping. | Postgres search (`ilike`/trigram): scales to thousands of recipes, more code today. |
| 2026-09-26 | One shared `RecipeForm` with `post` and `private` variants; private recipes get an auto slug and no photo | Reuses validation and the ingredient parser; photo uploads stay admin-only for now. | A separate library form: duplicated code. |
| 2026-09-25 | Merge grocery items in app code (`lib/grocery.ts`): same name (ignoring prep notes and simple plurals) and same unit only | Follows the PRD's v1 rule, is easy to unit-test, and reuses the ingredient parser. | Merge in SQL: harder to test and tweak. |
| 2026-09-25 | A grocery list is a saved snapshot, created with its items in one transaction (`create_grocery_list`) | Editing a recipe later doesn't change a list you're shopping from, and checked state persists. | Compute the list live from recipes: can't reliably remember checked items. |
| 2026-09-25 | Ticking items updates the screen instantly and saves from the browser; only the `checked` column is writable | Fast on a phone with weak signal; failed saves roll back with a message. | A Server Action round-trip per tap: slower in the store. |
| 2026-09-28 | Deploy via a public GitHub repo connected to Vercel | Every push to `main` redeploys automatically, and the public repo is the portfolio link. | Vercel CLI deploys from this machine: faster to start, no auto-deploys or public repo. |
| 2026-09-29 | Reviews are rendered into the cached post page; saving or deleting one revalidates that page | Review text and ratings stay in the HTML for search engines (and JSON-LD), and pages stay fast. | Load reviews client-side: always fresh, but invisible to crawlers and an extra request. |
| 2026-09-29 | Posting again updates your existing review (update first, insert only if none) | Keeps one review per user per recipe, and edits don't count toward the new-review rate limit. An upsert would also fail the column-level update grants. | Allow multiple comments per user: easy to stuff ratings. |
| 2026-09-29 | Delete buttons are shown client-side for your own reviews, or all reviews for the admin; RLS enforces the same rule | Moderation happens where the comment is, without making the page dynamic. | A separate moderation page in the dashboard: one more screen to build. |
| 2026-09-29 | Cached public pages refresh every 60 seconds (was 1 hour) as a fallback to on-save revalidation | `revalidatePath` only clears the cache of the server that ran the save, so edits made locally (or directly in Supabase) left the live site stale for up to an hour. | A Supabase database webhook that calls a Vercel revalidate endpoint: instant, but needs a secret and more setup than the MVP warrants. |
| 2026-09-29 | Delete actions confirm a row was removed and return an error message instead of throwing | RLS refuses silently (0 rows, no error), and thrown Server Action errors are hidden in production. | Throw errors: simpler, but users see nothing useful. |
| 2026-09-29 | Resize photos on the device before upload (max 2000px, JPEG q0.82) via canvas | Phone photos (3-12 MB) exceed the 5 MB bucket limit and are slow on mobile data; re-encoding also strips EXIF metadata such as GPS location from public photos. | Raise the limit and use Supabase image transformations: paid plan, and originals (with location data) would still be public. |
| 2026-09-29 | Keep one main photo per recipe, blog posts only (user's choice) | Matches the PRD; library recipes stay text-only so storage stays admin-only. | Multiple photos per recipe, or photos on private recipes: new table and per-user private storage. |
| 2026-09-29 | Admin role granted automatically from a private `admin_emails` table (DB triggers on sign-up, email confirmation, and list insert); only confirmed emails qualify | The role lives in the database RLS already uses, survives account recreation, and the email stays out of the public repo. Requiring confirmation stops someone claiming the address without inbox access. | Hard-code the email in a migration: simpler, but publishes it on GitHub. An app-side env var: RLS's `is_admin()` reads the DB role, so it would still need syncing. |
| 2026-09-29 | Send auth emails through Gmail SMTP with an app password (user's choice), on a dedicated Gmail account; switch confirmation links to token-hash `/auth/confirm` | Free and works without owning a domain; token-hash links work in any browser or device. | A custom domain + Resend: best deliverability and branded sender, but ~$10-15/year for the domain. |
| 2026-09-29 | Vitest 4 (dev-only) for unit tests and for Server Action flow tests with a fake Supabase client | Fast, TypeScript/ESM without extra config; flow tests exercise validation, DB calls, errors and redirects without touching the production database. Vitest 5 needs `@types/node` 22+, so 4 avoids changing the project's Node types. | Playwright end-to-end tests: more realistic, but need a separate test Supabase project (or Docker for a local one), which isn't set up. |
| 2026-09-30 | Drop Google sign-in; email and password only (user's choice) | R3 says "email or Google", so email alone meets it, and it avoids maintaining a Google Cloud OAuth app. `/auth/callback` stays for default-template confirmation links. | Finish the Google Cloud OAuth setup: one-tap sign-in for users, but another external service to configure and keep published. |
| 2026-09-30 | Any user can add a photo to their own private library recipes (user's request; replaces "blog posts only"). Photos go in a new PRIVATE `user-photos` bucket under `<user id>/`, with storage RLS limiting each user to their own folder | Private recipes need private photos; the public bucket would let anyone with the link view them. | Reuse the public `recipe-photos` bucket: simpler, but "private" photos would be publicly reachable. |
| 2026-09-30 | Private photos are shown through 1-hour signed URLs created on the server, rendered with `unoptimized` (no Next image optimizer) | Only the owner can sign their files, and private images never enter the shared image cache. Photos are already resized to ~2000px on upload. | Optimize them like public photos: slightly faster, but private images would sit in a shared cache. |
| 2026-09-30 | `recipes.photo_url` holds a public URL for blog posts or a private bucket path (`<uuid>/<uuid>.jpg`) for library recipes; validation enforces which is allowed per form | No change to `save_recipe` or the table, and one code path (`lib/photos.ts`) tells them apart. | A separate `photo_path` column: more explicit, but another rewrite of the save function. |
| 2026-10-01 | Food reviews are posts in the same `recipes` table with `kind = 'review'` plus `place_name`, `place_location`, `my_rating` (user asked for review posts) | Reviews reuse publishing, photos, URLs, comments, caching and the sitemap with no duplicated code; a DB check requires place and rating on reviews. | A separate `reviews` table: cleaner names, but duplicates the whole posting pipeline. |
| 2026-10-01 | Recipes live at `/recipes/<slug>`, reviews at `/reviews/<slug>`, each with an index page; slugs stay unique across both | Clear URLs per section for readers and search engines; one slug space avoids clashes. | One `/posts/<slug>` route: simpler routing, less descriptive URLs. |
| 2026-10-01 | Redesign after the user's reference (bold editorial food blog): Montserrat headings via `next/font`, photo cards with titles over the image, featured-post hero beside a colour block, pill buttons, Recipes/Reviews section nav, charcoal & tomato palette | Matches the requested look with less content (no newsletter, guides or shop). `next/font` self-hosts the font, so no request to Google. | Keep the previous minimal design: no work, but not the look the user wants. |
| 2026-10-01 | Site colours defined once as theme tokens (`brand`, `brand-dark`, `brand-soft`, `brand-tint`, `ink`, `paper`) in `globals.css` | The orange was hard-coded in ~15 files; now one edit re-colours the site. All pairs checked for WCAG AA contrast. | Find-and-replace colour classes per redesign: keeps the problem. |
| 2026-09-30 | Blog posts (R14-R17, inferred: the PRD on disk has no R14+) live in a new `blog_posts` table, admin-only writes, at `/blog` and `/blog/<slug>` | The overnight rules forbid changing existing tables, so `recipes.kind` couldn't gain a third value. | Add `kind = 'post'` to recipes: one pipeline, but alters an existing table's constraint. |
| 2026-09-30 | Blog bodies use a tiny text format (blank lines, `## ` headings, `- ` bullets) rendered as React elements | Enough structure for articles with zero HTML-injection risk and no new dependency. | Markdown via a library (e.g. react-markdown): richer, but a new dependency and sanitising to get right. |
| 2026-09-30 | Reading a not-yet-migrated `blog_posts` table returns "no posts" with a warning | Builds read the database, so builds (and deploys) pass before the migration is run. | Fail the build until the migration runs: stricter, but blocks every deploy on manual ordering. |
| 2026-09-30 | No comments on blog posts | `ratings_comments.recipe_id` references `recipes`, and the only allowed change to that table is a status column. | Separate blog comments table: possible later. |
| 2026-09-30 | Search (R19) is one parameterized SQL function, `search_posts`, over published recipes, reviews (incl. place names), blog posts, tags and recipe ingredients; full-text plus literal substring match, computed at query time | No table changes or indexes (overnight rule); parameters can't inject SQL; RLS still applies. Fast enough at blog scale. | Algolia or another search service: better ranking, but a paid external service. A stored tsvector column + GIN index: faster at scale, but alters existing tables. |
| 2026-10-01 | Collections (R20, inferred) group recipes already in the user's library; new `collections` + `collection_recipes` tables, private per user via RLS, max 50 per user (DB trigger) | Collections are a way to organise the library, so RLS only allows adding saved recipes; the cap keeps the UI usable. | Collections of any public recipe: more flexible, but overlaps with saving and needs extra cleanup rules. |
| 2026-10-01 | Admin 2FA (R21) uses Supabase TOTP MFA, enforced in the app (requireAdmin sends AAL1 sessions to `/mfa`) and in the database (`is_admin()` requires `aal = 'aal2'`) | One function change makes every admin rule (publish, delete, moderate, upload, audit) need 2FA, so a stolen password alone can't use the API as admin. | App-only check: simpler, but direct API calls with a stolen password would still have admin rights. |
| 2026-10-01 | Audit log (R22): new `audit_log` table, append-only in the database (no write policies, UPDATE/DELETE-blocking trigger, TRUNCATE revoked), admin-only reads. Blog changes are logged by a trigger on `blog_posts`; recipe/review/comment actions by the app via an admin-only `log_admin_action()`; app logging is best-effort | Database-enforced immutability. Triggers are the strongest source, but adding them to `recipes`/`ratings_comments` would change existing tables (overnight rule), so those go through the function. Best-effort so a logging failure never blocks publishing. | Triggers on every table: complete and tamper-proof, but alters existing tables. Fail the action if logging fails: stricter, but the site breaks whenever logging does. |
| 2026-10-01 | Moderation (R23): `ratings_comments.status` (the one allowed change), set by a DB trigger that holds comments with links, domains, email addresses or spam words as `pending`; users can't write the column; pending/rejected are visible only to the author and admin and excluded from averages; `moderate_comment()` approves/rejects and audits in one transaction | Enforced in the database, so neither the app nor a direct API call can skip moderation; simple rules catch the common spam without holding normal comments. | Flag in the app: easier to unit-test, but bypassable via the API. Hold every comment: safest, but slows every reader's comment. |
| 2026-10-01 | Baseline security headers (frame-ancestors none/X-Frame-Options, nosniff, strict referrer, HSTS, Permissions-Policy) via `next.config` headers; full CSP deferred | Cheap, low-risk protections against clickjacking and sniffing. A full CSP can break Next.js inline scripts and needs live testing. | A full nonce-based CSP now: stronger XSS defence, but risky to ship untested overnight. |
| 2026-10-01 | Multiple photos per post: new `post_photos` table (one row per extra photo, caption, position; parent is a recipe/review or a blog post), admin-written, replaced atomically by `set_post_photos()`; up to 12 per post; posts only (library recipes keep one photo) | Supersedes the earlier "one main photo" choice at the user's request. A table keeps order and captions queryable and needs no change to `recipes` (overnight rule). | An array column on `recipes`/`blog_posts`: simpler, but alters an existing table and makes captions/order clumsy. |
| 2026-10-04 | Password reset: "Forgot your password?" emails a recovery link (Supabase `resetPasswordForEmail`), which opens `/reset-password`; same response whether or not the email exists; 2FA accounts verify a code first (`insufficient_aal`) | The admin was locked out and real users need it. Identical responses prevent account probing; token-hash recovery links work in any browser. | Reset users by hand from the Supabase dashboard: fine for one admin, doesn't scale to readers. |
| 2026-10-05 | Email links (confirm sign-up, reset password) open `/auth/confirm`, a page with a button; the token is only verified when the button is pressed (Server Action), never on page load | University/corporate scanners (Microsoft Safe Links at VT) open every emailed link, which spent the one-time token, so real users saw "link already used". Scanners don't press buttons. | Verify on page load (previous route): one less click, but breaks for anyone behind a link scanner. |
| 2026-10-05 | Hide the Blog section (nav link, footer link, sitemap entry, home section) until a blog post is published; the root layout checks and revalidates every 60s, and publishing refreshes the whole site | The user mainly posts recipes and reviews; an empty Blog section looked unfinished. Nothing is removed, so blogging can start any time. | Remove the blog feature entirely: simpler, but it would need rebuilding later. |
| 2026-10-05 | During 2FA setup, keep the pending QR code/secret in `sessionStorage` (this tab only) and reuse the unverified factor after a reload; clear it on success; add "Start over" | Each page load used to delete the unfinished factor and make a new QR, so a phone reloading the tab after switching to the authenticator app left the user with a code that never matched. Supabase can't re-show a secret after enrollment. | Show the secret once and require starting over on any reload: simpler, but that's the trap the admin hit. |
| 2026-10-05 | Site icon as `app/icon.svg`, plus `apple-icon.tsx` and `opengraph-image.tsx` generated with `ImageResponse` (Next file conventions); posts without a photo name the default card explicitly | One SVG stays sharp at every size; generated PNGs stay in sync with the brand colours in code. A page that sets its own `openGraph` replaces the inherited image (checked), so photo-less posts point at `/opengraph-image`. | Hand-made PNG/ICO files: no code, but every colour change means re-exporting images. |
| 2026-10-05 | The share card fetches Montserrat ExtraBold (only the letters it uses) from Google Fonts when it is built, falling back to the default font on failure | The card is static, so this happens once per deploy and visitors never contact Google; a fetch failure can't break the build. | Committing the font file to the repo: no network at build time, but adds a binary to the repo. |
| 2026-10-05 | Personal details (Instagram URL, contact email) live in `lib/site-config.ts`; empty values hide the link | One obvious place to edit, reviewed in git, nothing secret about them. | Environment variables: editable without a commit, but need a redeploy anyway and are easy to forget in Vercel. |
| 2026-10-05 | Account deletion (R29) is a `delete_my_account()` security-definer function that deletes only `auth.uid()`; everything cascades; admins are refused; the app removes the user's private photos through the Storage API first | The app never holds a key that can delete any user, and the database guarantees a user can only delete themselves. Admin is blocked because posts cascade from the author. | A server action using the Supabase service-role key (`auth.admin.deleteUser`): simpler SQL, but puts an all-powerful key in the app. |
| 2026-10-05 | "Change password" on `/account` reuses the existing set-new-password page | That page already handles 2FA (`insufficient_aal`), weak and reused passwords; no second copy to maintain. | A separate form that also asks for the current password: stronger against a hijacked session, more code. Revisit if needed. |
| 2026-10-05 | Held-comment alert (R30) is a count: badge on the Dashboard nav link (read in the browser) and on Moderation, plus a banner on `/admin` | Works with no new secrets or services; public pages stay statically cached because the count is fetched client-side, only for the admin. | Email digest via SMTP (R40, Later): reaches the author away from the site, but needs the Gmail app password stored in Vercel. |
| 2026-09-24 | Grocery list items in a separate `grocery_list_items` table instead of a JSON `items` array | Checking off one item is a single-row update, and merging matching units is a simple query. | JSON array on `grocery_lists` (as in PRD): fewer tables, but every checkbox rewrites the whole list. |
